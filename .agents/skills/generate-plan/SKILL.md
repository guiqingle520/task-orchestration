# 生成计划(generate-plan)

目标:产出一份**能被驾驶舱解析、能通过校验器**的 `plan/plan.md`。驾驶舱只读取文件开头 `---` 之间的 YAML front matter。

## 必读文件
- `docs/PLAN_SPEC.md`:字段、规则、角色权限(以它为准)
- `plan/plan.template.md`:输出格式模板
- `plan/plan.md`:现有计划(如果存在)

## 步骤

### 1. 判断模式
- **新建**:`plan/plan.md` 不存在或用户明确要求重做。
- **增量更新**:已有计划。**必须保留**已有任务的 `id`、`status`、`progress`、`actualStart`、`actualEnd`,不得重写或重新编号。

### 2. 获取今天日期
以环境提供的当前日期为准(不要凭记忆)。所有日期用 `YYYY-MM-DD`。

### 3. 拆解需求
- 先定 1–3 个**里程碑**(可交付的阶段目标,`id: M1, M2…`,`due` 为交付日)。
- 再拆**任务**,`id` 用 `T-数字` 顺延(增量时取现有最大编号 +1)。
- 任务粒度:单个任务 0.5–3 天,能独立验收。超过 3 天继续拆;小于半天的合并。
- 每个任务必须归属一个里程碑,标题用"动词 + 对象 + 验收点"。
- 缺信息时(范围、人员、截止日)先向用户确认,不要臆造 `owner` 和 `due`;确实无法确认时,在「计划说明」里写明假设。

### 4. 排日期与依赖
- `deps` 只写**真实的前置**(没有它就无法开始),无依赖写 `[]`。禁止循环、禁止依赖自己。
- 任务 `start` 不得早于所有依赖的 `end`;同一 `owner` 同时并行的任务不超过 2 个(≥3 个驾驶舱会标红资源冲突)。
- 估时留 20% 缓冲;里程碑 `due` 不得早于其下最晚任务的 `end`。
- 工作日排期,默认跳过周末(除非用户另有说明)。

### 5. 初始状态值
- 新任务:`status: todo`、`progress: 0`、`actualStart: null`、`actualEnd: null`。
- 如果任务已经在做:`status: doing`,填 `actualStart`。
- 不要为未做的工作预填 `done`。

### 6. 写入并校验(强制)
1. 按 `plan/plan.template.md` 结构写入 `plan/plan.md`。
2. 运行 `node scripts/validate-plan.mjs`。
3. 失败 → 按报错逐条修复后重跑,直到输出 `✓ ... 校验通过`。**未通过不得结束任务,也不得开始编码。**

### 7. 记录变更
在「计划说明」末尾追加一行:`变更记录:YYYY-MM-DD <谁> <改了什么、为什么>`(例如新增任务、调整日期、改依赖)。日期调整必须写原因。

### 8. 向用户汇报(简短)
列出:里程碑与交付日、任务数量、关键路径(最长依赖链)、主要风险与假设、需要用户确认的问题。可提示用户打开驾驶舱 `npm start` 查看。

## 权限提醒
- 只有**规划者**能新增/删除任务、改依赖和计划日期。非规划者智能体发现计划需要调整时,只更新自己任务的 `status`/`progress`/`actual*`,并把调整建议告诉用户或规划者。

## 自检清单(写完逐项过)
- [ ] 字段名与模板完全一致,没有多余或缺失字段
- [ ] 每个任务都有 owner、milestone、start/end、deps
- [ ] 没有循环依赖;依赖的任务都存在
- [ ] 现有任务的 id/状态/实际日期未被改动(增量模式)
- [ ] `node scripts/validate-plan.mjs` 已通过
- [ ] 「计划说明」已追加变更记录

## 反例(不要这样做)
- 把任务写成"实现整个后端"这类无法验收的大块
- 用自然语言写日期("下周三")
- 为了通过校验而删除已有任务或把 `todo` 改成 `done`
- 修改 YAML 之外的内容并指望驾驶舱读取(正文不会被解析)
